reelocations: architecture

How a Reel shared on an iPhone becomes a pin in the web app and in the Google Maps app. This describes the code in this repository as of 2026-11-12. reelocations is self-hosted: each installer runs their own server with their own credentials. Every credential value below is a placeholder.

1. The pieces

2. From share to Google Maps

  1. Share (①). In Instagram the user taps Share → Save Reel to Map. The Shortcut (installed from the iCloud link, the user's personal link pasted once) takes a screenshot of the Reel and sends two JSON requests to https://<your-app>/api/intake/<personal link>: action=share (the Reel link, optional note, time) and action=media (the screenshot). The link identifies the user and their collection, so nobody signs in on the Shortcut. The Reel link alone carries only its ID, so the screenshot is the main source of text.
  2. Process (server). Each share starts a worker cycle at once. The pipeline reads the note and the screenshot (local OCR), looks the clues up in OpenStreetMap and, with a key, in Google Places to get the exact listing and branch, and asks OpenAI to read the screenshot only when the text is not enough (hard cap US$3/month). The result is one of three: a pin (sure), an Approximate pin that keeps its Review Queue entry (medium confidence), or a Review Queue entry only (unsure).
  3. Show (②). The web app (installable to the Home Screen) signs in with Google, shows the collection by country and city with type filters, Nearby, New and Starred, live through server-sent events. In the Review Queue the user confirms a place, or picks an option that replaces a pin or is added as another place. Every request is checked against collection membership.
  4. Save the real listing (③, ④). When the collection owner has connected a Google account once (npm run cli -- gmaps-connect; the session is kept privately on the volume), the server's Google Maps list publisher opens each new verified pin's listing by Place ID in headless Chromium, checks name and branch on the place card, and uses Google Maps' own Save to put it in the private list Reelocations. Google has no API for saved lists. Only Reels shared after the first connection are saved, each listing once; a save the branch check holds back goes to the Review Queue (This is the listing / None of these). Google then shows the list in the Google Maps app under You → Saved → Reelocations, where each place opens its normal place card. Verified end to end from Railway with a test account (six Reels; list and place cards checked on an iPhone).
  5. Optional: My Maps per country (⑤). A desktop publisher on the user's computer downloads finished pins from /api/publisher/export and writes one Google My Map per country in the user's own Chrome profile. These are custom pins at the listing's coordinates (You → Saved → Maps), and the computer must be on.

3. Credentials

Verified against src/config.ts, src/server.ts and .env.example. Your list (Google Sign-In, Google Places key, OpenAI key) is correct for the external providers, with two corrections: Google Sign-In needs only an OAuth client ID (no client secret: the server checks Google's signed ID token against Google's public keys), and the server will not start without APP_TOKEN, a secret you generate yourself. Neither Google provider key nor the OpenAI key is required to run the app.

4. Data and trust boundaries

  • One SQLite database and the screenshots live on the Railway volume /data; nothing user-specific is in the repo.
  • Collections are the unit of access: every API call, image and live-update stream is checked for membership.
  • Stars, New and opened places are per user; restaurant subtype corrections are per collection.
  • Nearby uses the phone's location inside the page only.
  • AI billing details are visible only to the account that runs the installation.
  • Leaving a collection ends access at once; deleting an account removes personal data, while places added to shared collections stay without the person's name.
