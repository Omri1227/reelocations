reelocations: architecture

How a Reel shared on an iPhone becomes a pin in the web app and in the Google Maps app. This describes the code in this repository as of 2026-11-12. reelocations is self-hosted: each installer runs their own server with their own credentials. Every credential value below is a placeholder.

1. The pieces

2. From share to Google Maps

  1. Share (①). In Instagram the user taps Share → Save Reel to Map. The Shortcut takes a screenshot of the Reel and sends two JSON requests to the user's personal intake link, https://<your-app>/api/intake/<intake-token>: action=share (the Reel link, optional note, time) and action=media (the screenshot as base64, with the Reel link). The token identifies the user and their collection, so nobody has to sign in on the Shortcut. The link alone carries only the Reel ID: Instagram's caption is not available to the app in a permitted way, so the screenshot is the main source of text.
  2. Process (server). Each share starts a worker cycle at once (and one runs every 60 s). The pipeline reads the note and the screenshot (local OCR), optionally speech from a screen recording (local Whisper), and extracts place clues. It looks them up in OpenStreetMap and, with a key, in Google Places to get the exact listing and branch. Only when the text is not enough does it ask OpenAI to read the image, inside a hard monthly budget. A confident result becomes a pin with the Reel link and a short quote; anything uncertain waits in the Review Queue.
  3. Show (②). The web app (src/web/map.html, installable to the Home Screen) signs in with Google, loads /api/places for the active collection and stays current through server-sent events. It groups places by country and city, filters by type and restaurant subtype, and offers Nearby (location stays in the page), New, Starred and the Review Queue. Every request is checked against collection membership on the server.
  4. Publish (③, ④). Google My Maps has no public API, so a small publisher on the user's computer, paired once with a desktop code, downloads finished pins from /api/publisher/export and writes them into one My Map per country with Playwright in the user's own signed-in Chrome profile. It reports back what it published. The Google Maps app then shows these maps under You → Saved → Maps. These are custom pins, and the computer must be on.
  5. Save the real listing (⑤, beta). Optionally the server itself saves each verified pin's actual Google Maps listing to a list (default Reelocations) in the owner's Google account, so it opens its normal place card in the Google Maps app with the computer off. Google has no API for saved lists, so the server opens the listing by Place ID in headless Chromium with a browser session the owner connected once (npm run cli -- gmaps-connect), checks the name and branch on the place card, and uses Google Maps' own Save. Approximate or ambiguous pins stay in the Review Queue, and so does a save the branch check holds back. Only Reels shared after the first connection are saved. Verified end to end from Railway with a test account (six Reels; list and place cards checked on an iPhone).

3. Credentials

Verified against src/config.ts, src/server.ts and .env.example. Your list (Google Sign-In, Google Places key, OpenAI key) is correct for the external providers, with two corrections: Google Sign-In needs only an OAuth client ID (no client secret: the server checks Google's signed ID token against Google's public keys), and the server will not start without APP_TOKEN, a secret you generate yourself. Neither Google provider key nor the OpenAI key is required to run the app.

4. Data and trust boundaries

  • One SQLite database and the screenshots live on the Railway volume /data; nothing user-specific is in the repo.
  • Collections are the unit of access: every API call, image and live-update stream is checked for membership.
  • Stars, New and opened places are per user; restaurant subtype corrections are per collection.
  • Nearby uses the phone's location inside the page only.
  • AI billing details are visible only to the account that runs the installation.
  • Leaving a collection ends access at once; deleting an account removes personal data, while places added to shared collections stay without the person's name.
